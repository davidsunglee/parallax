# Database login credentials are resolved per physical connection

The secret that authenticates a database login is produced by a Credential Source, and that source is asked every time the driver establishes a physical connection rather than once when configuration is built. Adapter configuration therefore carries two things: a connection string that says where the database is, and a credential declaration that says how the login it names proves who it is. A connection string that carries a login password is refused, so a secret has exactly one home.

The source is consumed by the concrete adapter and by nothing above it. The adapter is the only module that knows how its driver takes a password, and it is where the driver's per-connection establishment already happens. `Database.connect`, the adapter and runtime protocols, and both authority-selection operations are unchanged: the seam sits entirely below the runtime, nothing scopes automatically, and an application composes an adapter with a source exactly as it composes one with a retention policy.

The seam is one protocol, one credential kind, one declaration, and one error. A source produces a `Password`, a frozen record that keeps its secret out of every representation and that is its own source, so a constant credential needs no wrapper and a dynamic one returns the same type a static one is. The credential kind is a one-member alias, which a later bearer-token or client-certificate kind widens without renaming anything a provider already constructs. Driver-Managed Credentials is a declaration beside the protocol rather than a member of it: it resolves nothing, so it is never forced through a resolve operation and the alias stays one member. The declaration is mandatory and has no absent state, because a bare connection string used to mean "the password is in the string, or the driver finds it" and with the refusal it could only mean the latter — spelling it makes a reader see the choice on the line.

Resolution is per physical connection and not per acquisition. Established connections outlive the credential that opened them: a server does not drop a session because the token that authenticated it expired, so there is no refresh operation, no token cache, and no expiry field anywhere on the seam. Initial capacity, background growth, replacement after a drop, retirement by a maximum lifetime, and on-demand establishment each resolve; reuse of a retained connection resolves nothing.

Resolution may block, and bounding that is the source's own obligation. Unlike the other resource-free source protocols in the port, this one may reach a metadata service or a token endpoint. It runs on a pooling runtime's own worker threads, or — for an on-demand policy — on the acquiring caller's thread ahead of the driver's establishment limit, where nothing above it can interrupt it. A source that cannot bound its own I/O can stall an acquisition past every budget above it.

A refusal is classified rather than timed out. A pooling runtime creates most connections on a background path where a failure is logged and retried and never reaches a waiting caller, so a credential refusal is recorded on the same channel an initialization refusal already uses and named as the cause when startup or an acquisition gives up. Any exception a source raises that is not already a credential resolution failure is wrapped with fixed text and the original chained, so classification never depends on a provider's discipline and the driver's own log line — which prints the exception's text — carries nothing a source put in a message. Startup does not fail fast on a refusal: the runtime retries with backoff exactly as it does for a configure-time refusal, which tolerates a transient metadata-service error.

Secret hygiene is split by what each side can see. The credential record keeps its secret out of representations; the adapter's fixed-text wrapping keeps a careless top-level message out of the classified failure. Neither can scrub a cause a provider chose to chain, so that discipline is stated as the provider's.

The credential authenticates the Database Login Identity and is not a Database Authorization. One proves who the login is before a connection exists; the other is bound to an acquisition afterwards, as a replacement or containment of that login's privilege. A token-based identity integration authenticates the service login, and a principal then selects a role that login is a member of.

Alternatives rejected:

- Passing the credential to the operation that connects a Database Root splits "how to reach this database" across two arguments, grows the adapter protocol, and is bypassed by the plain runtime-holding constructor.
- Giving the resolve operation a neutral host, port and user parsed from the connection string is a partial promise: the adapter accepts the whole libpq grammar, including the empty string, service references, environment fallbacks, and multi-host lists resolved after the password is. Every field would be optional and every provider would carry a "may be absent" clause that only one integration ever exercises; the integrations that do need a target duplicate it in their own factory instead.
- Returning a bare string leaves secret hygiene with no single home and gives a later credential kind no place to land.
- An optional credential with an absent state preserves the ambiguity the refusal exists to remove.
- A wrapper record around a constant password makes an application spell two types where the dynamic case spells one.
- Detecting a password reachable through a driver's own service files or environment is not attempted: those are the driver's mechanisms, they are exactly what the driver-managed declaration asks for, and under an explicit source the resolved password wins by the driver's own precedence.
- A credential that also overrides the login is deferred. A broker minting a login per lease would make later connections authenticate as a different login than the one readiness captured, which is a provenance question about what that captured identity promises rather than a credential question.
